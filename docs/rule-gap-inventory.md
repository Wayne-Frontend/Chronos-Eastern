# 六事项规则缺口与入宅、安葬准入清单

核对日期：2026-10-19（Asia/Shanghai）。本清单依据当前 `main` 的事项表、六个规则包、规则引擎测试、来源台账与既有审计；另用卷十一公开转录检索入宅、安葬条目。清单初稿没有逐帧重读影印；同日后续已补核五张月表，证据见[出行审计 §8.13](travel-rule-audit.md)。本次没有修改规则取值或重算日期结果。转录只用于定位，新增结论须回到影印本校勘。

## 口径

- `supported` / `complete`：对应卷十一**单个用事条目**的宜忌已录全，现有可判定的卷十裁决例外已接入。它不表示整部历书的所有条件、六等第表或现实安排均已覆盖。
- `unresolved`：宜忌并见而无足够出处裁定时，保持不推荐。它是有来源的保守结论，不应一律当作程序故障，也不能用打分或“忌优先”消除。
- 下文“待核”表示需要文献或实现复核，**不是已确认的代码缺陷**。修改规则数据后必须递增对应包版本，并补命中、不命中、交节、冲突及来源回归。

## 共享缺口与实施顺序

### P1：先补可直接核对的证据

1. **月刑月表交叉核对（已完成）**：正月至十二月十二张均已核，最后五张的影印帧、原表值及代码比对见 [出行审计 §8.13](travel-rule-audit.md)。未发现差异，无须改动规则取值；既有审计中“待核七张／五张”保留为当时的历史快照。
2. **六包独立抽样（代表性案例完成，专项继续）**：已用同日六包矩阵核对宜命中、排除、常例未决、卷十解除、并见定忌及立春边界，见[独立日期案例复核](six-event-case-audit.md)。本事项独有规则仍须扩充影印案例；共享神煞的代码测试不能代替条目映射校勘。
3. **页面名与古籍名核对**：确认“开业／开市”“订婚／结婚姻”“提亲／纳采问名”在选项提示及详情中持续可见。此项只改善解释，不改变查询结论。

### P2：裁决研究，证据足够后才进入算法

1. **六等第表尚未录入**：卷十影印第 222 帧起为忌神煞、月组、建除日的矩阵。先逐格转录、双人复核并记录无法辨识格，再建立“原文格 → 条件 → 预期结论”的独立夹具。对可覆盖的冲突逐类试算，比较当前 `unresolved` 的变化；没有逐格证据前不修改引擎。
2. **适用射程必须分开**：卷十一用事自带的巳日、亥日等日支忌不在上述卷十神煞等第表的射程内；即使矩阵录入完成，也不能据表替这些冲突作裁决。其余无对应条款的冲突继续按常例说明。
3. **交节日口径**：当前整日按新节令月取值，卷四另有新旧两值并存的记载。先比较两种口径受影响日期、所需交节时刻精度与用户可理解的解释，再决定是否设计新规则模式；不能只换一个历法字段。

### P3：扩项前的规则准入门槛

每个新事项都需有**独立的古籍条目或明确的同条原注**、可核的影印定位、逐项宜忌与起例、可用的事实输入、卷十冲突适用范围、版本化规则包和上述边界测试。缺输入或缺出处的条件标为不可判，不能悄悄当作“未命中”；若只能覆盖日级条款，页面必须明确叫“日级文献参考”并披露未覆盖范围。

## 入宅：先确定是否存在可独立计算的条目

2026-10-19 起，入宅与安葬均从找日子页面的事项列表隐藏；以下保留的是内部状态与将来重新评估的准入条件，不是当前开发计划。

**现状**：事项表为 `reviewing`，没有规则包。仓库既有核查记录称卷十一三份用事清单及逐条宜忌均未检出“入宅”同名条目；本次对卷十一公开转录的检索也没有同名命中。“般移〈移徙同〉”有明确同条注记，不能据现代使用习惯把它改名成“入宅”。

可行路径按证据先后分两层：

1. **先定用户动作**：区分搬运迁居、首次进入新居、安床、修造等实际含义。若用户只是搬运迁居，继续使用现有“搬家＝般移／移徙”，并在选项解释中说明适用范围；这不产生一个独立“入宅”规则结论。
2. **若要单列“入宅”**：查找能够明确对应这一动作的原始条目，逐帧核对其与卷十一“般移”“安床”“修造”等条目的关系，并确认是否需要住宅坐向、仪式时辰或主事者资料。只有获得独立且可算法化的宜忌体系，才建立新事项与规则包。若证据只支持某一部分，应以受限名称和 `limited` 覆盖说明呈现；若没有可靠映射，继续 `reviewing`。

**停止线**：不从“搬家”复制规则包后更换显示名；不把不同条目按现代“乔迁”概念求并集或交集；不让缺少方位、时辰等输入的规则参与推荐。

## 安葬：可以研究日级条目，但须限定产品承诺

**现状**：事项表为 `unsupported`，没有规则包。卷十一转录可定位到**独立“安葬”条目**，与“破土”“启攒”分列；其日级宜忌值得继续校勘，但本次尚未逐帧复核影印。当前规则目录也没有“鸣吠”“复日”“重日”等安葬条目所需的原语。仓库既有产品边界还指出现实安葬安排可能需要山向、形势、时辰等本程序不收集的信息。

1. **文献层**：回看卷十一“安葬”完整影印页，核准宜忌列项；再逐项查义例起例和卷十裁决，尤其核对鸣吠、复日、重日及与破土、启攒不同的条件。建立原语表、来源定位和不可判条件清单。
2. **产品层**：先决定是否只提供“安葬日级文献参考”。若采用，页面必须明确不含山向、地形、时辰、逝者和家属条件，不称其为完整安葬择期，更不代替现实殡葬安排；只在可判范围内给出参考。若目标是完整实务择期，现有日期输入、事实模型与来源范围均不足，需单独立项研究后再决定是否提供。
3. **工程层**：在文献与产品范围确定后，新增独立规则包与版本、所缺日期事实、裁决适配和测试；对缺输入返回“信息不足”，对未决冲突保持不推荐。通过来源审计、跨月及交节回归和设备验收后，才考虑由 `unsupported` 改为 `limited` 或 `supported`。

**停止线**：不能把“安葬”看作“破土”或“搬家”的别名；不能只录入一部分宜项就给出完整推荐；没有明确范围与出处前不开放按钮。
